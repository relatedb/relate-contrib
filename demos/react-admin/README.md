# react-admin demo

A small administrative application over the embedded graph, with no server. It shows companies, people and projects as sortable,
filterable, paged lists, edit forms with pickers for related records, and a company page that lists its people and projects.
The records live in the visitor's browser and are still there after a reload.

It is built from [react-admin](https://marmelab.com/react-admin/), the [`@relate/contrib-react-admin`](../../packages/react-admin/README.md)
data provider, and an *application graph* of the core package ([`@relate/contrib-web`](../../packages/web/README.md)): a durable, named graph
that is seeded once. The decisions are in `design/adr/ADR-008` (the provider and this demo), `ADR-009` (application graphs) and
`ADR-010` (the catalog); the specification is `specs/008-react-admin-provider/`. RFC-005 and ADR-008 call this application a
*starter*; this demo and its documents say demo.

## Run it

From the repository root:

```sh
pnpm install
pnpm --filter react-admin-demo... run build     # builds the core, the provider and the demo
pnpm --filter react-admin-demo dev               # http://127.0.0.1:5190
```

On first run the page seeds 6 companies, 50 people and 10 projects, which are made up and generated by `pnpm seed` (a deterministic
script, `scripts/make-seed.ts`, whose output is `src/seed.json`). The seed is applied once and never over stored data.

## What is in it

- **Lists** of people, companies and projects: sort by a column, search (`q`), filter (a company, a minimum age, active, a status), and
  page. A filter reaches the provider as react-admin's filter object and becomes a statement with bound parameters.
- **Edit and create forms** with a picker for each reference (a person's company, a project's company and lead). Changing a picker
  moves a relationship.
- **A company page** that lists the company's people and projects through `getManyReference`.
- **A statement panel** (the collapsed section at the bottom) that shows each statement the provider sent to the embedded graph and its
  parameters. It is how the demo shows what a list, a filter or an edit turned into.
- **A storage notice** that says whether the records are stored durably in this browser, held in memory only, or waiting because
  another tab is using them, with a button that asks the browser to keep them. The browser is asked only when the button is pressed.
- **A reset control**, "Reset demo data": it offers a downloadable copy of the records first (the core's export), asks for confirmation,
  then discards the records and loads the demo data again.
- **Failure screens.** When the stored data cannot be opened (`store-newer`, `store-lost`, `store-unmarked`, `store-unreadable`,
  `import-interrupted`, `migration-failed`) the demo shows the reason in plain words and one choice, a confirmed reset. A failure
  screen offers no export: the core's `exportApplication()` rejects once a client has failed, so there is no way to copy the data
  out from there. Export is offered by the reset control, while the data is open.

## What a visitor loses

The records are stored in the browser's private storage for this site, in one application graph named `react-admin-demo`. They are
per browser: another browser, device or visitor has its own. **Clearing site data, or the browser freeing space, loses them.** The next
visit then starts from the seed; a visitor who had edited the data sees the demo data again, and a client that was open when the
data was cleared reports an error. The "keep my data" button asks the browser not to free the space, and the browser decides. A copy
made with the reset control's download is the only way to keep the records outside the browser.

A second tab of the demo waits while the first uses the data, says so, and continues when the first closes. It never writes while it
waits.

Resetting from the failure screen for `store-unreadable` also clears the origin's catalog file, the core's record of every graph
this origin has stored (ADR-010), because a catalog that does not parse is never written over. Other applications on the same origin
then find their stores without a record. On a shared origin, reset only after the other applications' data is safe.

## Copy it and make it yours

1. **Rename the store.** Two applications on one origin that use the same name share one store. Change `STORE_NAME` in `src/main.tsx`
   from `react-admin-demo` to a name of your own (letters, digits, dash and underscore), and the `STORE` constant of
   `tests/browser/state.ts` to `app-<your name>`.
2. **Change the schema.** Edit `src/schema.ts`: the resources, their fields (string, number or boolean, flagged sortable, filterable
   or searchable) and their references (many-to-one). Add or change the screens in `src/resources/`. The package makes the uniqueness
   constraints on `id` itself, so there is nothing to create in the store.
3. **Change the data.** Edit `scripts/make-seed.ts` and run `pnpm seed`, or replace `src/seed.json` with a graph data document
   (`design/adr/ADR-002`). Every node needs a unique string `id`. If you change the schema in a way that stored data must follow, raise
   the application's `version` in `src/main.tsx` and give it migrations (the core's README has the rule for them).
4. Nothing needs changing in `@relate/contrib-react-admin`.

## Dependencies

`react-admin` is pinned to an exact version, `5.15.6` (MIT), because a data provider depends on react-admin's filter, sort and
paging parameters. react-admin's paid add-on modules (the `@react-admin/ra-*` packages) are not used, and nothing here needs them.
The core, the provider and the engine's binary are workspace packages in this repository.

## Tests

```sh
pnpm --filter react-admin-demo test:react-admin-demo      # the seed, the failure table, the demo's terms (Node)
pnpm --filter react-admin-demo test:react-admin-browsers  # the demo in Chromium, Firefox and WebKit
```

The browser tests build the demo and serve it on port 5190, so stop `pnpm dev` first. They start from an empty origin each time
(WebKit runs in a persistent profile whose private storage is emptied between tests). They cover first run, sort, search and filters,
paging, the relation picker, the company page, a reload, deleting a company, the storage notice, a second tab, memory-only storage,
the persistence button, each failure, the loading shell, and the reset control with its download.
